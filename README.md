# Лабораторная работа 1: пересечение двух отсортированных массивов

**Задача.** Даны два отсортированных массива целых чисел длины M и N. Вернуть `true`, если у них есть хотя бы один общий элемент, иначе `false`.

## Структура

| Путь | Содержимое |
|---|---|
| `include/algorithms.hpp` | объявления четырёх алгоритмов |
| `src/two_pointers.cpp` | два указателя, O(M+N) по времени, O(1) по памяти |
| `src/binary_search.cpp` | каждый элемент меньшего массива ищется бинарным поиском в большем, O(M log N), O(1) |
| `src/exponential.cpp` | «два указателя», но по большему массиву шаг делается экспоненциальным (галоп) + бинарный поиск, O(M log(2N/M)), O(1) |
| `src/double_binary.cpp` | двойной бинарный: медиана меньшего массива ищется в большем, рекурсия по половинам, O(M log(2N/M)), O(log M) |
| `tests/test_algos.cpp` | тесты GoogleTest: граничные случаи, сравнение со `std::set_intersection` на случайных данных, перекошенные размеры, симметрия |
| `bench/bench.cpp` | код запуска замеров |
| `scripts/plot.py` | построение графиков (только стандартная библиотека Python, вывод в SVG) |
| `results/results.csv` | сырые данные (`algo,M,N,time_us`) |
| `results/bench_log.txt` | консольный вывод бенчмарка |
| `plots/*.svg`, `plots/*.png` | графики (PNG — растровые копии SVG) |

Во всех алгоритмах, кроме «двух указателей», в роли M берётся меньший массив, поэтому результат не зависит от порядка аргументов.

## Сборка и запуск

Нужны CMake ≥ 3.14 и компилятор C++17. Замеры имеют смысл только в Release.

```bash
cmake -S . -B cmake-build-release -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build cmake-build-release
./cmake-build-release/tests.exe
./cmake-build-release/bench.exe results/results.csv
python scripts/plot.py results/results.csv plots
```

## Методика

- **Данные: худший случай** (как рекомендовано в задании). Больший массив состоит из нечётных чисел `1, 3, 5, …`. Меньший состоит из чётных чисел, **равномерно распределённых** по всему диапазону большего: `small[i] = 2·⌊i·N/M⌋`. Общих элементов нет, поэтому каждый алгоритм проходит до конца, а элементы меньшего массива разбросаны по всему большему.
- **Размеры:** M, N ∈ {2⁴, 2⁵, …, 2²⁰}, все 17 × 17 = 289 пар, для каждой пары четыре алгоритма.
- **Замер:** прогрев, затем 7 серий по `reps = max(1, 2·10⁶ / (M+N))` вызовов. В CSV записана медиана из 7 значений среднего времени одного вызова. Таймер `steady_clock`.
- **Окружение:** Windows 11, MinGW g++ из CLion, `-O3` (CMake Release).
- Оси всех графиков логарифмические.

## Графики

- `plots/winner_map`: самый быстрый алгоритм для каждой пары (M, N). Число в клетке показывает, во сколько раз победитель быстрее второго места.
- `plots/equal_sizes`: время при M = N.
- `plots/fixed_M_*`: время в зависимости от N при фиксированном M (16, 4096, 2²⁰).
- `plots/ratio`: время в зависимости от соотношения N/M при N = 2²⁰ (M от 2²⁰ до 2⁴).

PNG получены из SVG через headless-браузер:
`msedge --headless=new --screenshot=plots/ratio.png --window-size=900,560 plots/ratio.svg`.

## Выводы

Главный параметр — **отношение размеров r = N/M** (N — больший массив). Абсолютный размер влияет мало, он только немного сдвигает границы.

1. **r ≤ 2–4: быстрее всего «два указателя».** При M = N этот алгоритм примерно в 2 раза быстрее экспоненциального, в 2,5–5 раз быстрее двойного бинарного и в 2,7–29 раз быстрее бинарного поиска (разрыв растёт с размером). У него последовательный доступ к памяти и нет ветвлений бинарного поиска. Для больших массивов (M ≥ 2¹²) он остаётся лучшим до r = 4 включительно.
2. **4 ≲ r ≲ 32: лучший — экспоненциальный (галопирующий) поиск.** При r = 8–16 он в 1,3–2,4 раза быстрее двух указателей. При r = 1 он медленнее двух указателей примерно в 2 раза.
3. **r ≥ 32: экспоненциальный, двойной бинарный и бинарный поиск близки между собой**, а «два указателя» отстают на порядки. Медианное отставание от лучшего: ≈ 20 раз при r = 256, ≈ 200 раз при r = 4096, ≈ 1500 раз при r = 65536. Медианный победитель здесь — двойной бинарный. Экспоненциальный и бинарный отстают от него до ~1,35 раза. Бинарный поиск догоняет остальных только при r ≳ 2⁸, когда log(2N/M) ≈ log N.
4. **Обычный бинарный поиск хуже всех при близких размерах:** при M = N = 2²⁰ он примерно в 29 раз медленнее двух указателей (O(N log N) против O(N)). Выбирать его стоит только при очень маленьком M.
5. **Влияние памяти.** При N = 2²⁰ (4 МБ, больше кэша L2) и M ≥ 2¹¹ время бинарного и экспоненциального поиска скачком растёт в 5–10 раз, хотя M увеличился всего вдвое. Скачок повторяется при повторном прогоне. На `plots/ratio` это видно как «ступенька» при N/M = 2⁸–2⁹. Вероятная причина: каждый поиск попадает в новые кэш-линии, а шаг N/M — степень двойки, из-за чего возникают конфликты ассоциативности кэша. Двойной бинарный страдает от этого меньше: рекурсия сужает диапазон, и соседние поиски работают с близкими участками памяти. Поэтому в этой области (M ~ 2¹¹–2¹², N = 2²⁰) он выигрывает у экспоненциального до 2,5–7 раз (точное значение меняется от прогона к прогону).
6. **Практическая рекомендация:** при N/M ≤ 4 использовать два указателя, иначе экспоненциальный или двойной бинарный поиск. Оба асимптотически оптимальны, O(M log(2N/M)). Экспоненциальный не требует памяти под рекурсию, а двойной бинарный устойчивее к промахам кэша на больших массивах.

Асимптотика подтверждается графиками. У «двух указателей» время растёт линейно по N даже при M = 16 (на `fixed_M_16.png` прямая с наклоном 1). У остальных алгоритмов при фиксированном M время растёт логарифмически.
